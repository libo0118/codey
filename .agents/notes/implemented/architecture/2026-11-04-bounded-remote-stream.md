# Agent Note: 有界首屏与公开状态增量传输

Status: implemented

## Problem

旧服务的只读采样观察到约 5 MB 的完整 state 重复发送，相同内容的多帧摘要一致；一次创建约一万个 DOM 节点和 2738 个详情块。当前源码仍整包输出公开历史，发送等待又与桌面读取共用循环。上述成本有直接证据，但尚未在手机复现断连，不能把所有断线归为同一原因。

## Decision

- 在现有认证会话流上以 `stream=2` 协商高效模式：首个匹配快照之后只发送带基准版本的公开增量，完全相同的公开状态不重发。已发布客户端继续使用原完整快照协议，不把原始 Native patch 下发；版本失配不继续启用写操作。
- 按用户确认的近期优先方式，首屏约二十项及软字节预算，较早内容按需展开，窗口耗尽后才允许用户显式补读 Native 历史。完整历史不删除，保留必要轮次控制元数据、稳定消息 anchor 和阅读位置，不引入持久化设置或全局展示缓存。
- 慢写入不阻塞原生读取和授权复验；每连接只保留最新待发公开状态，差异相对实际送达基底生成，不丢最终记录、不重放用户写操作。
- 复用已授权文件传输服务按需读取公开内嵌图片，不把大段 data URI 反复附在状态里；文件路径、同源鉴权、绑定撤销和私有快照边界不变。折叠详情只在展开时建立正文节点。
- 文件权限使用独立的 Native owner、数值 revision 和历史覆盖范围，不以每连接公开增量计数作为权限版本。较新且已覆盖的撤回不能由滞后 lease 或旧 snapshot 复活；未知来源、回退或 reset 使文件授权失效，不因此关闭仍匹配的有效聊天流。最后 lease 释放时清理授权状态，不持久化永久 tombstone。

## Alternatives considered

- 仅加大发送超时：改动少，但仍重复传输完整历史，且会延长原生读取被阻塞的时间，不能作为主要优化。
- 整体移植 Mobile Bridge 的历史存储、长轮询及激活流程：它已有近期先行和按变更更新，但会替换现有 owner、会话及文件授权流程；只借鉴有界首屏和增量思路，保留 Codey 原生及安全边界。
- 把缓存当成实时连接：首屏快，但过期缓存不能证明当前 owner、权限和任务状态，仍需匹配的新鲜原生快照。

## Verification

- 合成大历史中，单项变化不再发送整个历史；重复状态不产生数据帧，增量重建与对应公开快照一致。
- 首屏及按需历史不删记录、不改变模型、owner、provider、cwd、审批或消息顺序；旧完整协议及新旧客户端连接均有回归。
- 慢消费者不积累无界状态，不阻塞授权撤销与原生读取；代次失步拒绝继续使用旧状态，草稿保留且写操作不自动重放。
- 图片解析仅返回元数据，实际字节按需传输；未知路径、跨会话及已撤销绑定仍拒绝读取。
- 比较真实组件在 320/390px 下的首屏节点和渲染负担，所有数据及网络模拟标为 Mock，不把它称作手机现场验证。

生产组件合成 Mock 的首帧样本为 7112809→52456 字节、DOM 为 32732→273，单项 delta 229 字节只重绘目标消息，prepend 阅读锚点误差约 0.15px。此样本不是真实 Rust 编码输出或手机测速；Rust 的首帧、增量、慢写、文件数据源及授权回归交由 CI 实际执行。本机没有 `link.exe`，格式与 metadata 校验不能替代原生执行。

## Consequences

近期窗口和增量降低重复传输及首屏节点成本，权限范围不随展示裁剪收缩或扩大；代价是需要按需展开旧内容。Native 首次快照、owner 等待和 Native IPC 大帧限制仍可能影响冷进入，不靠缩短等待后盲目 open 抢占已有窗口。大单项或旧客户端仍有传输成本。现场安装版本为旧候选，最终预览需用户空闲时手动更新复测；不自动升级、发送或重启，尚不能宣称全部手机断连已消除。
